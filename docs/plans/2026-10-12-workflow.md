# Workflow: design

The design of the piece `workflow` of [the philosophy overhaul](2026-10-07-philosophy-overhaul-roadmap.md), settled with the owner in an interview on 2026-10-12.
The roadmap's section "workflow" holds what was settled before the interview.
This file holds what the interview added or changed, and the split into changes.
It is transient: the last change of the piece removes it.

## Design

### Goal

A prompt or an issue comes in, and proof and a pull request come out.
Nothing waits for approval unless the owner asked for a gate.
The nine skills vendored from superpowers go, with the plans, the two review gates, the owner gates and the execution ledger.
Fourteen skills and six playbooks vendored from pstack take their place, at upstream commit `9f451cf875ad1239912762f67741e8e5ba6ac0f1`.
One of the playbooks becomes a skill of its own, so the devkit gains fifteen skills and five playbooks.

Done means:

- A session in a Lyngon repository starts with the standing instructions and with nothing else of the workflow.
- Only the operator switches the mode on, by invoking `/build:auto` with a task.
- Every change ends in a pull request whose title and body are the squash commit, checked in CI.
- No shipped text names a skill that does not exist, and a check fails when one does.

### Approach

The workflow has three layers, and each one is complete without the layer above it.

1. The standing instructions reach every session through a hook. They hold what every change needs: when to ask, how a change is branched, checked and handed over, and when to read the principles and record a mistake.
2. Skills the agent may start on its own, each on its own trigger. `build:pull-request` and `build:correction` are among them, so handing over and learning do not depend on the mode.
3. The mode, `/build:auto`, which the operator invokes with a task. It adds routing to playbooks, delegation rules and the proof and reply rules.

Four mechanical decisions carry the rest: the pull request is the commit, a plugin has no version, provenance is recorded per upstream, and a development plugin assumes the whole bundle.

The alternatives, and why each lost:

| Decision | Chosen | Rejected, and why |
| --- | --- | --- |
| How the mode reaches a session | Standing instructions in every session, the mode only on `/build:auto` | The whole mode in every session, because the owner wants the mode to be a choice per task. A pointer that tells the agent to invoke the mode, because it can be skipped and it makes the mode a default. |
| Where the version bump happens | No version, so the commit SHA is the version | One fragment file per change, folded on the default branch, which needs a job that commits to the default branch and a fold tool. A bump in each pull request, where two changes write the same line. |
| What a provenance record covers | One upstream at one commit, in `catalog/vendored/` | One record per skill, which is 14 pairs of files for one commit. One record per plugin per upstream, which ships provenance into every installed plugin. |
| Which plugin holds what | `build`, `discover` and `writing`, by concern | One plugin per job (route, design, prove, review), which gives eight plugins that name each other in cycles. |
| How plugins depend on each other | Members of `all` declare no dependencies and assume the whole bundle | Declared dependencies kept acyclic. The settled pointers between `principles` and `build` already run both ways, and Claude Code's documentation does not say what a cycle does. |
| What is left of prerequisites | A development plugin assumes a Lyngon development repository, `writing` assumes nothing | The four prerequisites and their conditional headings. They served repositories without Nix and devenv, which `INTENT.md` lists as a non-goal. |
| How a skill change is proven | `claude plugin eval` at the base commit and at head | Blind runs judged by hand (pstack's `eval` playbook), a hand-rolled version of what the tool does. |
| Where the merge message lives | The pull request body | A comment or a "Merge message" block in the body, a second text that goes stale and costs a paste per merge. |
| What `approach` becomes | The explicit design gate, invoked only by the owner | Deleting it, after which every gated piece would spell the same request out in words. |

### Facts the design rests on

Each is marked as measured (in this session, on Claude Code 2.1.283, 2026-10-12) or as documented (in Claude Code's documentation, read the same day).

- An invoked skill survives a compaction. After the compaction boundary the transcript holds an `invoked_skills` block with the skill's full text (measured).
- That block keeps the first 5,000 tokens of each skill and 25,000 tokens in all, filled from the most recently invoked skill (documented).
- The Skill tool refuses a skill marked `disable-model-invocation: true`, with "it is reserved for explicit user invocation" (measured).
- Such a skill cannot be preloaded into a subagent (documented).
- A SessionStart hook's output enters the context, is capped at 10,000 characters, and runs again after a compaction (documented).
- A plugin from a relative path in a git-hosted marketplace, with no `version` in its manifest or its marketplace entry, gets the commit SHA as its version (documented).
- `claude plugin eval` compares a run with the plugin against a run without it, and publishes its report to claude.ai unless told not to (documented).
- `lyngon/devkit` allows all three merge methods, and its squash message defaults to the commit messages (measured).

### Components

#### The standing instructions

The `build` plugin's SessionStart hook prints `plugins/build/hooks/standing-instructions.txt` on every session start, a compaction included.
It replaces the `conventions` hook, which shrinks to one line about its own skills: "Invoke the conventions skill for a file's kind before you edit that file. No conventions skill loads on its own."

The text, with the path filled in by the hook:

```text
This is a Lyngon repository. These are its standing instructions, and they count as being asked.

Principles first. Before any work that takes judgment (a design choice, a refactor, a bug fix, a test, a measurement, a script, a document, a question to the operator), invoke principles:index and read the file of each principle that applies. Its text is not in your context until you invoke it, and working from your memory of it is the mistake this paragraph exists to prevent. This repository's own principles are the files under .claude/rules/.

Decide and act. Ask only before an irreversible action, or for a product or preference call that no run can settle. Always ask before a merge, a push to the default branch, a force-push, a tag, a release, a publish, a deploy, deleting data or a remote branch, any message outside GitHub, and spending money. Stop at a gate on requirements, a specification, a plan or tasks only where the owner asked for one, and then stop exactly there.

A change is one concern, delivered as one pull request.
- Work on a branch named <type>/<slug>, started from the up-to-date default branch. Never commit on the default branch.
- Commit as you go, without asking. Branch commits are free-form, because the pull request lands as one commit.
- Nothing enters the environment without a declaration that a lock file pins. A tool, anything run from the PATH (jq, a linter, an interpreter, uv itself), goes in devenv.nix. A dependency, anything a package imports, goes in that package's manifest through the workspace's package manager. A library's manifest states constraints, never pins, and the lock file pins. A development tool that has to load the workspace's own packages or plugins (pytest, eslint) counts as a dependency. A secret is declared in secretspec.toml, and its value never enters the repository.
- The full check is `devenv test`. Run it before every push, and never disable, skip or weaken a check or a hook to get past it.
- When the change is done and the full check passes, invoke build:pull-request. It pushes the branch and opens the pull request without asking. The owner reviews the pull request and decides the merge.
- Fixes after a push are new commits. Never rewrite pushed history without asking.

When the operator corrects you, a review finding is accepted or a change is reverted, invoke build:correction.

If the operator started this session with /build:auto and its text is no longer in your context, read <path>/skills/auto/SKILL.md before you continue.
```

`validate-marketplace` fails when the file is longer than 4,000 characters, because every session pays for it.

The bullet about declarations states one rule for a tool, a dependency and a secret: an install that no file records is forbidden for all three.
Its sentence about development tools is what the repository already does, stated once.
pytest and import-linter sit in the development group of the root `pyproject.toml`.
The TypeScript compiler and ESLint with its plugins are development dependencies of the root `package.json`, because the ESLint of nixpkgs cannot load the workspace's plugins.
ruff, prettier, basedpyright and tflint come from nixpkgs, since none of them has to load the workspace.

The last sentence is the answer to the compaction budget.
A mode session that invokes every skill a feature needs comes near 25,000 tokens of skills, and the mode is the oldest, so it is the first to drop.
The sentence costs one line in every session, and re-reading happens only in a session that invoked the mode and lost it.

#### The mode and its playbooks

`plugins/build/skills/auto/SKILL.md` is Lyngon's rewrite of `poteto-mode`.
It carries `disable-model-invocation: true`, so the agent can never start it.
The operator starts it as a slash command, with the task as its argument.
It holds:

- The routing triggers, each naming a skill the devkit has.
- The index of the five playbooks, and `build:figure-it-out` for a task that matches none.
- The delegation rules: a delegate that writes code is the `build:implementer` agent, a new piece of work goes to a fresh subagent, and the lead owns every delegate's diff.
- The proof and reply rules: every claim carries its evidence or its label (measured, inferred or guess), and nothing is handed to the operator to check that the agent could run.
- The rule for comments.

It does not hold the gate, the principles or the pull request format.
It points at the standing instructions, `principles:index` and `build:pull-request` for those.

`validate-marketplace` fails when the file is longer than 15,000 characters, and when it lacks the flag.
At four characters to a token that is 3,750 tokens, a margin under the 5,000 that a compaction re-attaches.

The playbooks are files under `plugins/build/skills/auto/playbooks/`: `feature.md`, `refactoring.md`, `bug-fix.md`, `prototype.md` and `autonomous-run.md`.
Each states what must hold when the task is done and what proof is owed.
A step survives the rewrite only when it is a fact the reader cannot derive, as `prescribe-proof-not-steps` demands.
Each ends by invoking `build:pull-request`.

#### Agents

Two files under `plugins/build/agents/`.

`implementer.md` is the delegate that writes code.
It cannot preload a flagged skill, so its definition tells it to read the mode's file in full before any work.
It builds the scope it was given, does not push and does not open a pull request, and reports what it did with the proof.

`comment-auditor.md` is pstack's Comment Sicko without the persona.
It keeps the keep-list and the flags, reports only, and never writes application code.

#### The pull request is the commit

The agent starts `build:pull-request` on its own whenever a change is ready, in every session.
What must hold when it is done:

- `build:clean-comments` ran over the diff.
- The full check passed on the pushed head.
- The title is `<type>(<scope>): <subject>` in Conventional Commits form.
- The body is under the target length that `check-pull-request` reports.
- The body has exactly these headings, in this order:

```text
## Why
## Decisions
## What changed
## Scope
## Blast radius
## Verified
## Not verified
```

- The pull request is open and ready, not a draft, and the agent reports its link.
- After every later push the body is true again, because the body describes the whole change as the commit will.

What each section holds:

- `Why` gives the problem and the approach, in one to three sentences.
- `Decisions` names, for each decision, what was decided, the alternatives and how they were compared, the trade-off accepted and the steering document changed. An entry that replaces a decision record says `replaces <name>`. "None" is written out.
- `What changed` has one to three bullets, with both sides of a rename.
- `Scope` says what the change covers and what it deliberately leaves out.
- `Blast radius` says who or what the change touches, and why that is safe or risky.
- `Verified` has one to three bullets, each a command or a run path and what it showed.
- `Not verified` says what the change claims or touches that no run covered, and why. "None" is written out.

Evidence too long for the body goes in a pull request comment that Verified points at.
The body carries no vendor line, because it becomes the commit message.
Without a remote the skill commits and reports the title and the body.
With a remote and no forge tool it pushes and hands over the link the forge printed.

The length of the body is set per repository through the baseline, as a target and a headroom above it:

```nix
lyngon.pullRequest.body.targetLines = 40;    # lib.types.ints.positive
lyngon.pullRequest.body.headroomLines = 20;  # lib.types.ints.unsigned
```

The limit is the target plus the headroom and is never set on its own.
No pair of values can then disagree, and the option types reject a zero target and a negative headroom without an assertion in the module.
The check counts content lines, which are the lines that are neither blank nor one of the seven headings.
The headings and the blank lines around them are the same 21 lines in every body.
Counting them would leave 19 lines of content at a target of 40, and Decisions, the section `discover:why` needs most, would run out first.
`check-pull-request` warns above the target and fails above the limit, and a headroom of 0 makes the target the limit, with no warning zone.
Every warning and failure prints the numbers, as in "body is 64 content lines, limit is 60 (target 40 plus headroom 20)", and names the ways out: move a decision into a decision record, move evidence into a pull request comment, or split the change.
In CI a warning is an annotation on the pull request.
The skill states no number, since a skill cannot read a Nix option.

The same check runs locally and in CI.
`devenv/check-pull-request.py` is a baseline command, `check-pull-request`, that reads the title from `PR_TITLE` and the body from `PR_BODY`.
The baseline module builds the command and writes the two length values into it as arguments.
A local shell and CI build it from the same `devenv.nix` and `devenv.lock`, so both check against the same numbers.
It fails on a title that commitizen rejects, on a missing, extra or misordered `##` heading, on a body over the limit, and on an em dash, an en dash or a curly quote in either.
The workflow `.github/workflows/pull-request.yml`, with one job named `pull-request`, runs it on the `pull_request` events `opened`, `edited`, `synchronize` and `reopened`.
The workflow passes the title and the body through the environment and never interpolates them into a command, since anyone can write them in a public repository.
It is a workflow of its own, because an `edited` run that skipped the test job would report that job as passed.
`repo:init` writes the file, so the example tree in the README gains a line.

The commitizen and `prose-lint-commit-msg` hooks leave the baseline, since branch commits are free-form.

#### The mistake ledger

One file per mistake, `docs/mistakes/<name>.md`, named after the mistake:

```md
# <The mistake, as a sentence>

- **Date**: 2026-10-12
- **Caught in**: [<pull request title>](<pull request link>)

<What happened, in two or three sentences.>
```

`build:correction` writes the file on a correction from the operator, an accepted review finding or a revert.
A failing check does not trigger it.
Before it writes, it reads the ledger.
On a repeat it writes the check that makes the mistake fail and deletes the ledger file, and a repeat that no tool can decide becomes a file under `.claude/rules/`.
When the mistake is caught before its pull request exists, `build:pull-request` adds the link after it opens the pull request.

`plugins/build/skills/correction/scripts/prune-mistakes.py` deletes the files whose date is older than the limit, and `build:correction` runs it every time.
The limit is the baseline option `lyngon.mistakes.maxAgeDays`, 365 by default, which reaches the script as `LYNGON_MISTAKES_MAX_AGE_DAYS`.
`validate-documents` checks the shape of a ledger file, so the script never meets a date it cannot read.

`encode-lessons-in-structure` routes a first occurrence to the ledger instead of the pull request.

#### Provenance per upstream

A provenance record covers what the catalog took from one upstream at one commit.
It is `catalog/vendored/<upstream>.md`, and there are four: `pstack.md`, `mattpocock.md`, `noodle.md`, and `superpowers.md` until the last change deletes it.
Records of pinned plugins stay where they are, `catalog/<plugin>.md`.

A record holds the upstream, its commit, its version, its license and the reviewer, then why it is here, a table of what was taken and where each piece went, the local patches per destination and the review notes.
The upstream license sits once in `shared/LICENSE-<upstream>`, under the same name as the record, and is symlinked to the root of every plugin that holds its text.

`validate-marketplace` fails when a record lacks a header line, when a destination does not exist, when a plugin that holds a destination lacks the license link, and when a skill directory holds an `UPSTREAM.md` or a license file.
The existing records move in the same change, so there is one way.
`/devkit:add-skill` takes several paths of one upstream in one pass and writes into the record.

All skills from one upstream move together at a bump.

#### No versions

Every local `plugin.json` loses its `version`, and every plugin its `CHANGELOG.md`.
The rule file `every-plugin-change-is-versioned.md` goes.
`validate-marketplace` fails on a `version` in a local manifest, and its message says why: the commit is the version, and a version field would hold every user on it.
A pinned plugin keeps the version in its marketplace entry.

What a repository learns of an update is the squash commits under the plugin's path, and a breaking change is the `!` in the title:

```sh
git log --oneline -- plugins/build
```

#### The whole bundle is assumed

A plugin in `all` assumes a Lyngon development repository: Nix, devenv, the baseline, the documents, the workflow and every other member of `all`.
`writing` assumes nothing.
The structure stays a choice per repository.

- The prerequisites `documents`, `workflow` and `baseline`, the devenv condition, their conditional headings, the `Prerequisites:` lines and the README column go. `docs/conventions/prerequisites.md` goes with them, and the validator's messages carry the reasons.
- `core` goes.
- A member of `all` declares no `dependencies`. `all` and `devkit` keep theirs.
- `With the Lyngon structure` remains the one conditional heading, checked as today, with `repo` and `devkit` exempt.
- `repo:init` asks whether the repository adopts the structure, where it asked which prerequisites it adopts, and always enables `all`.

`validate-marketplace` gains two checks.
A `<plugin>:<skill>` in shipped text that names no existing skill fails.
A reference from `writing` to another plugin, or a development term in it, fails.
The development terms are the ones the validator lists today for the documents, devenv, the baseline and the structure.

#### Scripts and their tools

A script that a skill runs ships as source next to the skill, so the two update together.
The baseline declares the tools: the option `lyngon.scriptTools`, a list of packages that every shipped script may use, `[ pkgs.python3 ]` by default and added to the shell.
The consumer's `devenv.lock` pins them.
The devkit's test runs each shipped script with an empty PATH and exactly that list.
A hook that runs at session start is outside the rule, because it runs before the environment is exported.

Two scripts ship: the ledger's prune script and the helper of `build:work-trace`.
Both are Python.

#### Skill proof

A change that alters what an agent does (a new skill, a changed procedure or trigger) owes an eval case for the behaviour it claims, and the suite's score at the base commit and at head, both under Verified.
A change of wording alone owes the validators.
Evals run on the author's machine with `--no-publish`, never in CI.
The rule lives in a rule file of the devkit, since no check can carry it.

The suite runs from the repository root, where a case can name the plugins folder and so load every plugin from the checkout.
`compare-evals` runs it at a base commit and in the working tree and prints both scores.
The README's section "Evals" documents both commands and says what keeps a case steady.

A run that grants Bash needs two things from the machine, and the README's section "Evals" names both.
The sandbox refuses the run while `~/.aws` holds a symbolic link inside it, and every command of the run ends with status 127 while `bwrap` and `socat` are not on the system's PATH.
The owner's machine provides both since 2026-10-13.
A command of a run finds the tools of the devenv shell through the hook of the `devkit` plugin, so the cases of `012-the-flow` that drive git and the baseline's commands can run.

#### Terms

`CONCEPTS.md` changes in the change that makes each term true.

Two terms change their definition, and six are new.

- Workflow is the way of working in a Lyngon repository, where a prompt or an issue comes in, the agent decides and acts under the standing instructions, and proof and a pull request come out for the owner to review and merge.
- A Provenance record is the file that documents what the catalog took from one upstream, at which commit, under which license, who reviewed it, where each piece went and which local patches it carries.
- The Standing instructions are the text every agent session in a Lyngon repository starts with, saying that it is a Lyngon repository, when to ask, how a change is branched, checked and handed over, and when to read the principles and record a mistake. To avoid is "baseline", which is the devenv module.
- A Mode is a way of working that an operator switches on for one task by invoking a skill, and that adds routing, delegation and proof rules to the standing instructions.
- A Playbook is a file of a mode that says, for one kind of task, what must hold when it is done and what proof is owed.
- A Gate is a point where an agent stops until the owner answers. One always holds, before an irreversible action and for a product or preference call that no run can settle. Any other exists only where the owner asked for it.
- Proof is something a reviewer can rerun or read that shows a claim holds.
- The Mistake ledger is the directory that holds one file per mistake an agent made in the repository for the first time, kept until the mistake repeats and gets a check, or ages out.

Vendored skill says that the license is in its plugin and the record in the catalog, and Bundle says that `all` is the bundle.
Plan, Review gate, Owner gate, Pre-approval, Acceptance line, Dictated text, Mandated check and Prerequisite go, with their lines under Relationships.

#### Where the lines of `conventions:engineering` go

A line is kept only where it reaches the session that needs it, or where a check fails without it.
`shared/STRUCTURE.md` does neither on its own: it reaches a session only as a reference file of `repo:init` and `repo:add-package`, so no row names it as a carrier.

| Line | Goes to | How it reaches the session |
| --- | --- | --- |
| Weigh decisions toward final quality, little weight to development cost | A new Lyngon principle, `weigh-quality-over-cost` | A principle in the index |
| Simplicity is part of quality, no speculative abstraction, no configuration for a case nobody has | The same new principle | A principle in the index |

### Data flow

A task reaches a session as a prompt, later as an issue.
The standing instructions are already in context.
The agent invokes `principles:index`, reads what applies and works on a branch.
With `/build:auto` the mode matches a playbook, which may route to `discover:how`, `build:architect`, `build:arena` and `build:review` and delegates code to `build:implementer`.
Without it the agent works directly and still invokes the skills whose triggers match.

When the change is done, `build:pull-request` runs `build:clean-comments`, the full check and `check-pull-request`, pushes and opens the pull request.
CI runs the full check and the same `check-pull-request`.
The owner reviews and squashes, and the title and the body become the one commit on the default branch.
That commit is the plugin's new version and its changelog entry.

A correction, an accepted finding or a revert goes to `build:correction`, which writes a ledger file or, on a repeat, a check.

### Error handling

- A compaction drops the mode: the standing instructions, printed again after the compaction, tell the agent to read the mode's file.
- A subagent or the agent itself calls the Skill tool on `auto`: the tool refuses. `build:implementer` reads the file by path and never calls the tool.
- `check-pull-request` fails: the agent fixes the title or the body, and the `edited` event runs the check again. A body over the limit is cut by one of the ways out that the message names. The agent never raises the two options to make a body pass, since that weakens a check.
- `check-pull-request` warns: the pull request still passes, and the warning stays visible on it.
- The full check fails: the agent fixes the cause or reports the failure with its output. Nothing is weakened.
- No remote, or no forge tool: as under "The pull request is the commit".
- An eval cannot run (no credentials, a refusing sandbox): the pull request says so under Not verified and makes no claim.
- A ledger file has an unreadable date: `validate-documents` fails the commit. The prune script exits with an error and deletes nothing.
- A parent of a stacked change gets review fixes: the child merges the parent. Nothing is force-pushed.
- A rewrite leaves a pointer to a skill that is gone: the reference check fails.

### Decisions made without asking

The owner saw these during the interview and did not object.
They are listed so that the review of this file can.

- The mistake ledger lives in `docs/mistakes/`.
- A gate the owner asks for produces a file under `docs/plans/` on the branch, and the agent stops with one question.
- `build:review` runs when a design is contested or the blast radius is large, not on every pull request. `build:clean-comments` runs before every pull request.
- No worktree is mandated. A second change in the same checkout gets its own.
- The two agents are `implementer` and `comment-auditor`.
- `approach` ends at the owner's approval. Work then proceeds under the standing instructions, and under the mode only if the owner invokes it.
- The `conventions` plugin keeps a one-line hook for its own skills.
- An `approach` session counts as the owner asking for a design, which is what lets the agent reach for `build:architect` there.

Decided after the interview, in writing this file and in its review:

- The standing instructions end with the sentence about a lost mode, instead of a hook that re-injects the mode.
- All seven headings of the body are always present, and no other `##` heading is allowed.
- The length of the body counts content lines only, and the two length values reach the command as arguments that the baseline writes into it.
- The pull request check is a workflow of its own, which adds a required check to the ruleset.
- `weigh-quality-over-cost` becomes a Lyngon principle, two lines about tests become a local patch to one pstack principle, and "end to end, as a user meets it" to another.
- The bullet about declarations in the standing instructions also covers secrets, and the `repo` hook's text gains two sentences that no check carries yet.
- `user-invocable: false` is allowed in `conventions` and nowhere else.
- The helper of `build:work-trace` is rewritten in Python, and its log is never committed.
- `build:pull-request` fills in the link of a ledger file written before the pull request existed.
- `/devkit:add-skill` takes several paths of one upstream in one pass.
- `approach` carries the flag, like `auto`, so the pieces 004 to 007 start with the slash command and `add-skill` interviews with `discover:interview`.

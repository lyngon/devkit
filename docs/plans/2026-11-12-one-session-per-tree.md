# One session per working tree

The design for issue 121: two live Claude Code sessions can work in one working tree, and neither learns about the other.
The owner settled it in an interview on 2026-11-12, in the Claude Code session "issue-121-one-session-per-tree" (`2f17664b-f934-4c24-8fd9-fa687ddcf840`).

This file is transient.
It lands on the default branch with the decision records, ahead of the implementation.
The implementation starts in a fresh session, on a branch of its own from the default branch of origin, once this design and the fix of issue 154 have merged.
The change that finishes the work removes this file.
What must outlive the work is in the three decision records under Goal and in `CONCEPTS.md` (**Live session**).

## Goal

A session that starts or resumes in a working tree where another live session works moves into a worktree of its own before it changes anything there.
A session alone in its tree stays where it started.
The decisions are recorded in three files:

- [a-session-moves-to-its-own-worktree-when-another-works-in-its-tree](../decisions/a-session-moves-to-its-own-worktree-when-another-works-in-its-tree.md)
- [the-session-check-fails-open-when-the-registry-is-unreadable](../decisions/the-session-check-fails-open-when-the-registry-is-unreadable.md)
- [session-start-never-removes-a-worktree-or-a-branch-it-holds](../decisions/session-start-never-removes-a-worktree-or-a-branch-it-holds.md)

Done means:

- In a working tree where an earlier live session works, busy or idle, the repo plugin refuses a later session's `Edit`, `Write`, `NotebookEdit`, `Bash` and `Monitor` calls.
  The refusal names the earlier session and gives a way forward that works from where the later session is.
  Every other tool still runs, `Read`, `EnterWorktree` and `ExitWorktree` among them.
- The refusal lifts once the later session has moved, or once the earlier session has ended, crashed or been killed.
- The earlier session is never refused, and neither is a session alone in its tree.
- This holds for Nix CLI sessions with and without `--worktree`, for VS Code sessions and for headless sessions, and for a subagent of any of them, wherever the session's process has the devenv environment.
  A session without it runs no Python hook at all, which issue 156 makes visible.
- When the check cannot find its own session in Claude Code's registry, it refuses nothing, and session start says that nothing stops a second session in this tree.
- `.claude/worktrees/` is ignored in every clone with the repo plugin, and in the `.gitignore` that `repo:init` writes.

## Facts the design rests on

Measured on 2026-11-12 with Claude Code 2.1.283, in headless sessions in a scratch repository, unless a line says otherwise:

- Claude Code writes `~/.claude/sessions/<pid>.json` for every live session: one JSON line with `pid`, `sessionId`, `cwd`, `procStart`, `entrypoint` (`cli`, `sdk-cli` for headless, `claude-vscode`), `name` and `status` (`busy` or `idle`).
  `procStart` equals field 22 of `/proc/<pid>/stat`.
  The format is undocumented, and the documented `ListAgents` tool shows the same sessions.
- The session's own file exists when its SessionStart hook runs.
  A hook's parent process is the session process.
- After `EnterWorktree`, the registry `cwd`, `/proc/<pid>/cwd`, a hook's `$PWD` and the hook input's `cwd` all name the worktree.
  `CLAUDE_PROJECT_DIR` stays at the launch root.
- A resumed worktree session's SessionStart hook still sees the launch root.
  The session enters its worktree about 0.4 s later, and its PreToolUse hooks see the worktree.
- A second `--worktree` session with a name already in use opens the same worktree, and Claude Code neither refuses nor warns.
- After `kill -9`, the session's registry file stays, with `status` `busy`, and so does its worktree lock.
  A worktree lock also names a dead pid after a clean headless exit and after a resume.
- The live VS Code session in lyngon.com (pid 737133) had no `--name`, and its registry `name` was generated by Claude Code.
- A hook runs with the environment of the session's process only, never with what a SessionStart hook wrote to `CLAUDE_ENV_FILE` (measured on 2026-11-14 with Claude Code 2.1.321).
  So in a session started without the devenv environment, no Python hook of any plugin runs: issue 156.
- Read in the tool descriptions, not measured: `EnterWorktree` tells the model to use it only when the user, `CLAUDE.md` or memory asks for a worktree, and creates a new worktree only from outside a worktree session.
  `ExitWorktree` leaves only a worktree that `EnterWorktree` created in the same session.

## Alternatives compared

- **A worktree for every session**, rejected by the owner.
  Every session would pay a devenv entry of 5 to 24 s, `tofu init` per root module in lyngon.com, no access to the main checkout's `tmp/` and Claude Code's worktree guard.
  Two sessions can still meet in one worktree by name or by resume, so detection is needed anyway.
- **Warning or asking the operator, then carrying on**, rejected because two sessions keep sharing the tree.
- **Telling the later session without refusing anything**, rejected because an instruction is not concurrency control, and an unattended `/build:auto` run can skim past it.
- **Markers that the plugin's own hooks write and remove**, rejected.
  Claude Code's registry already holds one entry per live session, with the process start time that tells a live session from a dead one.
  Markers of our own would repeat it, and they would need a SessionEnd hook, which does not run after `kill -9`.
  The registry is undocumented, so the check fails open and says so.
- **Liveness from worktree locks**, rejected because a lock outlives a kill, a clean exit and a resume.
- **The check at session start**, rejected as the authority, because a resumed session's SessionStart hook sees the launch root and not the worktree it enters.
  The check runs before each call, where the refusal needs it anyway.
- **The check in bash**, rejected because it parses JSON.
  It is a Python program on the standard library, like the build plugin's PreToolUse hooks, and runs with the baseline's `lyngon.scriptTools`.

## Components

### The session check

`plugins/repo/hooks/one-session-per-tree.py`, a PreToolUse hook in `plugins/repo/hooks/hooks.json` with the matcher `Edit|Write|NotebookEdit|Bash|Monitor`.

- Its own session is its parent process.
  Its tree is the nearest ancestor of its working directory that holds `.git`, so a linked worktree is a tree of its own.
- A live session is a file under `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/sessions/` whose `pid` runs with the recorded `procStart`.
  A file whose process is gone, or whose pid now belongs to a process with another start time, is not a live session.
  That is how a crashed session's file expires.
- Another live session works in this tree when the nearest ancestor of its registry `cwd` that holds `.git` is this tree.
- The earlier of two sessions has the smaller `procStart`, then the smaller pid.
  A resumed session starts a new process, so it is the later one.
- When an earlier live session works in this tree, the hook denies the call.
  Its reason names the earlier session (its name, `entrypoint`, `status` and how long it has been idle), the tree and the branch checked out there.
- The reason gives the way forward that works from where the later session is:
  - When its task continues the work on the branch checked out there, it asks the operator to close the other session.
  - Otherwise, from a tree that is not a worktree session of its own, it calls `EnterWorktree` with a name of its own.
  - Otherwise, in a worktree it cannot leave by itself, such as a `--worktree` worktree shared by name, it asks the operator to close the other session or to start this one again under another worktree name.
- The reason says that the operator's standing instructions ask for the move, because `EnterWorktree`'s own description holds the model back unless someone asked for a worktree.
- When its own session has no readable entry, the hook allows the call and says nothing.
  Session start reports that.

### Session start

`plugins/repo/hooks/session-start.sh` gains two duties:

- It says so when this session has no entry in Claude Code's registry, in one line naming the directory it looked in.
- It makes the clone ignore `.claude/worktrees/`: when no ignore rule covers the path, it appends `/.claude/worktrees/` to `info/exclude` in the clone's common git directory.
  A repository set up before `repo:init` wrote the line has no such rule, lyngon.com among them.

### The `repo:init` file set

The `.gitignore` baseline in `plugins/repo/skills/init/references/repo-files.md` gains `.claude/worktrees/` beside `.claude/settings.local.json`.

### Documents

- `plugins/repo/README.md` describes the PreToolUse hook and the two new duties of session start, with what was measured.
- Each decision record under Goal gets the name of its check under `Enforced by` once the check exists.

## Proof owed

- **A test of the session check**, run by `devenv test` with only `lyngon.scriptTools` on the PATH.
  It builds a repository with a linked worktree under `.claude/worktrees/`, and a config directory whose registry entries belong to helper processes that the test starts.
  It runs the hook as the child of a helper with its own entry, and asserts the exact decision and reason for each of these cases:
  - the later session in the main checkout, refused;
  - the earlier session there, allowed;
  - a session alone in a linked worktree, allowed;
  - two sessions in one linked worktree, the later refused;
  - an entry whose process was killed, ignored;
  - an entry whose pid runs with another start time, ignored;
  - its own entry missing, allowed.
- **A test of session start** for the registry line and for the exclude: added once, and not again on a second run, or when `.gitignore` already covers the path.
- **A live run with two real sessions**, in the restricted headless setup the owner approved for the probes.
  The setup is `--permission-mode default` with only `EnterWorktree`, `ExitWorktree` and `Bash(sleep:*)` allowed.
  Neither prompt mentions worktrees, so the refusal alone has to make the later session move.
  The later session's Bash call in the shared main checkout is refused with the reason above.
  It calls `EnterWorktree`, and its next Bash call runs in its worktree.
  Then the earlier session is killed with `kill -9`, and a third session's Bash call in the main checkout runs.
  A second pair shares one `--worktree` worktree by name, and the later session follows the way forward its refusal gives.
  The pull request quotes the hook decisions from both pairs.
- **A check in a VS Code session in lyngon.com** that the hook runs there and refuses, and that the model there moves.
  The VS Code session measured on 2026-11-12 had no `python3` on its process PATH, and a hook gets nothing else, so this check waits for issue 156 to say how a VS Code session gets the devenv environment.

## What issue 141 must respect

Issue 141 makes session start delete local branches whose changes are already in the default branch.
Under this design:

- It deletes no branch that a worktree holds: the branch checked out in any worktree, and `worktree-<name>` while `.claude/worktrees/<name>` exists.
  A `worktree-<name>` branch sits at its starting commit, so it passes both of 141's tests, and only this rule keeps it.
- It removes no worktree, live or dead, clean or not.
- It needs no liveness check.
  If it ever does, liveness comes from the registry and `procStart`, never from a worktree lock.
- Two sessions can start at the same moment in one clone, so a branch that is already gone counts as deleted.
- Its session start may run in a later session that is about to be refused.
  Deleting branches stays safe there, because refs are shared by every worktree and only branches with nothing new go.

[session-start-never-removes-a-worktree-or-a-branch-it-holds](../decisions/session-start-never-removes-a-worktree-or-a-branch-it-holds.md) states the first two points, so they outlive this file.

## Out of scope

- Every devkit session loads its plugins from the main checkout's files, so a branch switch there changes the plugins of every devkit session: issue 147.
- A session keeps the devenv environment of the tree it started in after `EnterWorktree` or a resume into a worktree: issue 154.
  Its fix merges before the implementation starts, so a session that moves runs with the environment of its own tree.
- A session started without the devenv environment runs no plugin's Python hook, this check included, and nothing says so: issue 156.
- Removing leftover worktrees, which session start never does.

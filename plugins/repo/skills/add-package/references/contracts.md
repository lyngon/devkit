# Contracts

A contract is the published boundary shape of an app: DTOs, never domain objects.
It is consumed by the provider's entrypoint (server stubs) and the consumer's adapters (clients), and never by a domain or application layer.

## Directory

```text
contracts/{name}/
├── schema.yaml           the source of truth: OpenAPI, protobuf or JSON Schema
├── devenv.nix            the generate task and the freshness hook
├── README.md             what the contract covers, who provides and who consumes it
├── python/               generated library package, a member of the uv workspace
├── typescript/           generated library package, a member of the pnpm workspace
└── conformance/          handwritten: the invariants the schema cannot express
```

One generated package per consuming language, no more.
This is the one place a language name is a path segment.

## Generated packages

Generated code is committed.
The manifest of each generated package is handwritten once and its source tree is regenerated by a task.
A hook regenerates on every commit that touches the schema or the generated packages and fails when the result differs, the same way this devkit keeps its README table fresh:

```nix
{ pkgs, ... }:
{
  tasks."{name}:generate" = {
    description = "Regenerate the {name} client and server packages from the schema";
    exec = "cd contracts/{name} && {generator command}";
  };

  git-hooks.hooks."{name}-fresh" = {
    enable = true;
    name = "{name} contract is fresh";
    entry = "sh -c 'cd contracts/{name} && {generator command} && git diff --exit-code -- .'";
    files = "^contracts/{name}/";
    pass_filenames = false;
  };
}
```

The generator comes from `devenv.nix`, so its version is pinned with everything else.
Generate both the client and the server-side stubs from the same schema so the two sides cannot disagree.

## Conformance

The conformance package holds the invariants the schema cannot express: a returned id is valid for the other operations, create creates, list reflects what was created.
It is written once, in one language, against the generated client interface:

- a library target exposing the suite as a function that takes a client (or a fixture in the test framework's terms);
- a thin executable wrapper that builds the generated HTTP client from a base URL and runs the suite, for providers in another language and for deployed environments.

The contract never starts a provider.
Each provider's test target starts itself and hands its URL, or an in-process client, to the suite.
A provider in another language runs the wrapper over the wire from its `devenv.nix` test task.
An in-memory fake of the provider runs the same suite; passing it is what "implements this contract" means.
